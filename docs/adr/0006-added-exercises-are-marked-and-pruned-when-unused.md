# An Added Exercise is marked on its Session entry, and dropped at End Session if unused

A Session can now gain an Exercise its Workout didn't list (an **Added Exercise**, see `CONTEXT.md`). Three decisions came with that, each of which looks like a mistake without the reasoning.

**The mark is stored on the entry, not derived.** `SessionExerciseEntry.addedMidSession` is set when the Exercise is added. We could have computed "added" by comparing a Session's entries to the Workout's current Exercise list. We didn't, because the Workout is editable after the fact: add an Exercise to Push Day tomorrow and every past Session that happened to contain it would silently stop being "added". ADR-0001 exists to stop later Workout edits from rewriting a Session, and a derived mark would do exactly that. The flag is optional, so existing Sessions and exports need no migration, and its absence means "the Workout listed it".

**An unused Added Exercise is dropped at End Session, while an unused Workout Exercise is kept.** ADR-0004 keeps a skipped Exercise's empty entry because the entry records what the Workout contained that day. An Added Exercise was never in that plan, so an empty entry would record a skip of something nobody meant to do: a mis-tap or a changed mind would appear in history as an abandoned Exercise. "Unused" uses the same test as Set pruning (no Set carries any measurement), so an Added Exercise holding a half-typed weight is kept, and the Remove action before End Session refuses on the same test. Remove is therefore never able to discard a number that End Session would have kept.

**The mark stays after the Exercise is kept in the Workout.** At the end of a Session the lifter can add the Added Exercises they used to the Workout. That appends to the Workout and leaves the Session alone, `addedMidSession` included: that Session did add it that day, and the next one will list it as a plain Workout Exercise, with its Carried-Over Shape and Ghost Values read from the Session that added it. The offer is derived live each time (used, still existing, not already listed) and nothing about a declined offer is stored, so a declined Exercise is offered again the next time it is added and used.

Considered a separate list of extra Exercises on the Session. Rejected because every consumer (cards, Ghost Values, pruning, history, export) would have to merge two lists, to carry one bit of information. Considered allowing the same Exercise twice, as a second block. Rejected because the Store and the UI key every entry by Exercise id, and a second entry would be unreachable; it would need an entry id of its own. Considered falling back to another Workout's history for an Added Exercise's Ghost Values. Rejected for now: ADR-0004 scopes hints to the Workout because the same Exercise is loaded differently across Workouts, and an accepted hint is stored as a real measurement.
