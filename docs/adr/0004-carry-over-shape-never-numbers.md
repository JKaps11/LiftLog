# A new Session carries over the shape of past work, never the numbers

`startSession` used to copy the previous Session's Sets wholesale, weights and reps included, so a Session opened looking as though every Set had already been performed — and because `endSession` only stamped `endTime`, untouched copies were persisted as real performance, feeding the next Session's copy and any future strength graph. We decided a Session opens with Pending Sets instead: the **Carried-Over Shape** (how many Sets, solo or left/right pair) comes from the most recent Session that Logged that Exercise in that Workout, while the measurements do not. Last Session's numbers appear only as Ghost Values — placeholder text inside empty fields, never stored — and entering a measurement is itself the act of Logging the Set, so `SessionSet` measurement fields are present if and only if the Set was performed. Untouched Sets are pruned at End Session, keeping the Exercise's entry with an empty Set list so a skipped Exercise still records that it was part of that day's Workout.

The lookback is per-Exercise rather than per-Session, because pruning means an Exercise skipped last week has no Sets to take a shape from, and scoped to the same Workout, because the same Exercise is loaded differently across Workouts and a heavy Bench Press on Push Day should not suggest itself during a Full Body Session.

Considered keeping the pre-fill and marking provenance instead — colouring carried-over values and clearing the colour on edit, or storing `carriedWeight`/`carriedReps` beside the real fields. Rejected because the need being served is "where am I, what's left to do?", and a provenance marker cannot answer it: repeat last week's weight exactly, change nothing, and the row stays marked as carried-over while the Set has in fact been performed — the failure landing precisely on accessory work, where repeating numbers is most common. Storing carried values additionally persists display scaffolding into permanent records and every export, leaving a lasting ambiguity about which field is true.

Considered a sentinel for "not performed" (`weight === 0`) to avoid touching the schema at all — rejected because zero is a real weight for bodyweight movements, and because it cannot distinguish a carried-over `135` from a confirmed `135`, which is the entire problem.

Considered an explicit per-Set completion gesture, as Hevy and Strong use. Rejected because their checkmark is tolerated for doing double duty as the rest-timer trigger, and this app has no rest timer, so the tap would be pure overhead. Accepting a Pending Set is instead folded into focusing its first field, which fills the whole row from its Ghost Values — one tap, cheaper than the typing it replaces.

Consequences worth naming: Ghost Values are read from the previous Session live while the current one is open. This does not violate ADR-0001, which governs stored history not mutating retroactively, but it does mean editing an old Session mid-workout shifts today's Ghost Values. Clearing a field returns a Set to Pending, which is the only un-accept path and is deliberately not a designed gesture. Sessions already stored with `{ weight: 0, reps: 0 }` pre-fills will read as Logged; no migration is planned, as no real history exists yet.
