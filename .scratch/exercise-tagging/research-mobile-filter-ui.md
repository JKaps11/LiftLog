# Research: mobile exercise-list filter/browse UI patterns

Context: LiftLog is a single-user mobile PWA (React 19, Tailwind, shadcn/ui on base-ui), `max-w-md`, mobile-only. Exercise list is about to grow from a flat searchable list of strength exercises (see `src/features/exercises/ExercisesPage.tsx`, `src/features/workouts/WorkoutForm.tsx`, `src/features/workouts/exerciseLookup.ts` — currently just `filterExercisesByName`, a plain case-insensitive substring match, no grouping/filtering at all) toward ~50-300 items spanning strength + stretch/mobility work.

Every claim below is tied to a URL I fetched or whose exact quoted text I verified via search-engine snippet of the live page (noted inline where WebFetch could not render the page directly, e.g. Apple HIG and Material M3 are client-rendered SPAs that returned empty bodies to the fetch tool — in those cases I quote text the search engine indexed directly off the real page and cite that page's own URL, not a mirror).

---

## 1. Pattern comparison

**Search-only (current LiftLog state).** `filterExercisesByName` in `src/features/workouts/exerciseLookup.ts` does `exercise.name.toLowerCase().includes(normalized)` — no ranking, no grouping, no filters. This is fine at low N but degrades as N grows because: (a) it requires the user to already know/recall the exercise name (bad for browsing/discovery of stretches they haven't logged before), (b) there's no way to answer "what stretches do I have" without typing something that happens to match many names, (c) a single flat `<ul>` with no virtualization means scrolling becomes the only browse mechanism at 300 items.

**Grouped/sectioned lists (alphabetical or by category).** Apple's own HIG guidance on **Lists and tables** (verified via search-engine snippet of `developer.apple.com/design/human-interface-guidelines/lists-and-tables`, since the page is JS-rendered and WebFetch returned empty) states groups can be indicated by style: *"Some styles use visual details to help communicate grouping and hierarchy... In iOS and iPadOS, for example, the grouped style uses headers, footers, and additional space to separate groups of data."* It also documents the **alphabet index** sidebar pattern for long lists: *"An index typically consists of the letters in an alphabet, displayed vertically at the trailing side of a list. People can jump to a specific section in the list by choosing the index letter that maps to it."* (Apple's own Contacts app is the canonical example of this pattern.) This is a low-cost, low-chrome pattern well suited to a single-user list: no extra controls, just section headers + optional index rail, and it works for both alphabetical grouping and category grouping (e.g. "Legs", "Push", "Mobility").

**Search + category tabs.** Good when items belong to *one* dominant category and the category count is small and stable (~4-8). Material Design 3's own **Lists** component docs describe an optional grouping wrapper: *"an optional wrapper around two or more list elements to be grouped together, with optional heading text displayed above each list in a group"* (quoted from `m3.material.io/components/lists`, verified via search snippet — direct fetch returned only the page title). Tabs work well only if a user is reliably going to know which tab an item is under; with cross-cutting concepts like "mobility that's also lower-body," tabs force an arbitrary single bucket unless you duplicate the item across tabs.

**Search + filter chips.** Material 3's **Chips** docs (`m3.material.io/components/chips`, verified via search-engine snippet since direct fetch returned only the title) describe exactly this pattern: *"Chips help people enter information, make selections, filter content, or trigger actions"* and specifically for filter chips: *"Filter chips use tags or descriptive words to filter content... can be a good alternative to toggle buttons or checkboxes... Multiple chips can be selected or unselected... Filter chips can be shown underneath a search field, and filter chips can wrap to a new row, and if there are more than two rows, consider using horizontal scrolling."* This is the pattern built for exactly the multi-tag, multi-select case (item can match more than one active filter simultaneously) and is explicitly designed to sit under a search field — but it adds a persistent row of UI chrome above the list at all times, which is more visual weight than a 50-300-item single-user list strictly needs if most sessions are "search for the one thing I want."

**Tradeoffs for a single-user list of a few hundred items (not multi-tenant/social):** the deciding factors here are different from a public app store: there's no need to optimize for discovery/marketing-driven browsing, no algorithmic recommendation surface, and the same person built the taxonomy they're filtering — so the categorization can be minimal and self-consistent rather than needing to anticipate arbitrary users' mental models. That argues for the lightest pattern that still lets the user narrow ~300 items down to a handful in 1-2 taps: sectioned/grouped list (for browsing when they don't remember a name) plus search (for when they do), with filter chips added only if/when a single grouping axis turns out to be insufficient (see §2).

## 2. Multi-dimensional categorization (cross-cutting tags, e.g. "mobility" + "lower body")

**Single primary category vs. multi-select tags** is a real, well-documented tradeoff, not unique to this app:

- **Hevy**'s official custom-exercise flow (`hevyapp.com/features/custom-exercises/`, fetched directly) uses exactly a hybrid model for this problem: *"you can select a primary muscle (say, the chest) and multiple secondary targets (say, the abs, shoulders, and triceps)"* — i.e. one **required primary category** (used for the main grouping/browsing view) plus an **open multi-select set of secondary tags** (used for filtering only, not for primary grouping). This maps directly onto the "mobility" + "lower body" case: primary category could be a single required field (e.g. "type": strength/mobility) while muscle-group tags are a secondary multi-select used purely for filter chips.
- **Jefit**'s exercise database (`jefit.com/exercises/bodypart.php`, fetched directly) takes the opposite approach — pure multi-dimensional filtering with no forced primary bucket: separate filter dimensions for muscle/body part, equipment, type (strength/stretching/powerlifting/olympic), and difficulty, combinable simultaneously, no single "home" category per exercise.

**Compact mobile UI for exposing multi-select filters**, per the primary component docs already surveyed in §1 and §3:
- **Horizontal-scrolling chip row** — Material 3's own guidance (`m3.material.io/components/chips`) explicitly recommends this for chip overflow: wrap to a second row, then switch to horizontal scroll beyond two rows. This is the standard compact-mobile answer to "many possible tag values, narrow viewport."
- **Bottom sheet / modal filter panel** — used when the tag list itself is long enough that even a scrolling chip row is too much permanent chrome; the trigger is a single "Filter" affordance that opens a sheet with the full set of options. Apple Fitness+'s own Filter feature works this way per Apple's support documentation (`support.apple.com/guide/fitness-plus/find-workouts-and-meditations-apdcd80997be/ios`, fetched directly): tapping "Filter" opens a picker where the user "select[s] any filter you want to apply" (by trainer, duration, music genre, activity type) rather than showing all filters as permanently-visible chips.
- **Scope control + tokens inside the search field itself** — Apple's HIG **Search fields** page (`developer.apple.com/design/human-interface-guidelines/search-fields`, verified via search-engine snippet of the live page) documents this as the sanctioned way to combine categorization with search on a single control: *"a scope control acts like a segmented control for choosing a category, while a token is a visual representation of a search term that acts as a filter... Use a scope control to filter among clearly defined search categories... If appropriate, let people refine the scope by enabling supplementary scoping rules using filter rows that appear beneath a scope bar... To avoid overwhelming people, consider only showing filters that are relevant and contextual."* This is the closest sanctioned platform pattern to "search + a couple of quick filter toggles" without a separate persistent chip row.

Takeaway for cross-cutting tags: a forced single "primary category" (Hevy's model) is the cheaper UI to build and reason about, and is sufficient if you only need it to drive a grouped/sectioned browse view; genuinely orthogonal multi-select tags (Jefit's model, or MD3 filter chips) are the right tool only once you actually need "show me mobility AND lower-body" simultaneity, which for a personal list of 50-300 items may not arise often enough to justify the extra chrome.

## 3. Concrete component mapping for shadcn/ui (base-ui) + Tailwind

All fetched directly from `ui.shadcn.com/docs/components/*` (shadcn) and `base-ui.com/react/components/*` (underlying primitive), current as of today.

| Pattern | shadcn/ui component | Underlying base-ui primitive | Notes from the docs |
|---|---|---|---|
| Category tabs (single active category) | **Tabs** (`Tabs`, `TabsList`, `TabsTrigger`, `TabsContent`) | **Tabs** (Root/List/Tab/Indicator/Panel) | shadcn: "organizes content into layered sections... displayed one at a time." base-ui: keyboard arrow-key navigation, focus looping, horizontal/vertical orientation. Good for a small, stable, single-select category set — not naturally suited to multi-tag membership. |
| Filter chips (multi-select toggle set) | **ToggleGroup** (`ToggleGroup`, `ToggleGroupItem`) | **Toggle Group** | shadcn: "a set of two-state buttons that can be toggled on or off," supports `type="single"` or multi-select. base-ui: `multiple` prop — when true, "press[ing] more than one toggle at a time" is allowed, unlike default exclusive mode. This is the direct shadcn primitive for MD3-style filter chips; style it with rounded/chip-like Tailwind classes and wrap in an `overflow-x-auto` row for the horizontal-scroll behavior MD3 recommends. |
| Search + fuzzy/incremental filtering with grouping | **Command** (built on `cmdk`) | n/a (cmdk, not a base-ui primitive) | shadcn: "command menu for search and quick actions." Composed of `CommandInput` + `CommandList` + `CommandGroup`/`CommandSeparator` + `CommandEmpty` — i.e. it already gives you search-input-driven filtering *and* grouped/sectioned results (e.g. group by category) in one component. This is the single component that most directly matches "search plus grouped/sectioned list" from §1, and could replace the current bespoke `filterExercisesByName` + flat `<ul>` in `WorkoutForm.tsx` and `ExercisesPage.tsx`. |
| Bottom-sheet style filter panel | **Drawer** or **Sheet** (`side="bottom"`) | Drawer is its own base-ui-backed component; Sheet extends the Dialog primitive | shadcn Drawer docs explicitly describe it as acting like "a bottom sheet on mobile devices," with swipe-gesture support, height capping (`calc(100dvh - 6rem)`), and snap points — this is the more mobile-native, gesture-friendly choice. Sheet's `side="bottom"` option achieves a similar visual result via the Dialog primitive but without Drawer's swipe/snap-point affordances. For a phone-only PWA, Drawer is the closer mobile-native match; Sheet is fine if swipe gestures aren't needed. |
| Collapsible grouped sections (accordion-style category list) | **Accordion** (`Accordion`, `AccordionItem`, `AccordionTrigger`, `AccordionContent`) | Accordion | shadcn: "a vertically stacked set of interactive headings that each reveal a section of content," one open at a time by default or `multiple` to allow several open. Useful if you want category sections to be collapsed by default (saves scroll length at 300 items) rather than always-expanded like a plain sectioned list. |

None of Tabs, ToggleGroup, Command, Drawer/Sheet, or Accordion docs mention anything mobile-specific being *withheld* — all are usable at `max-w-md`; Drawer is the one explicitly designed around mobile/touch (swipe, snap points, iOS Safari handling).

## 4. Platform guidance (Apple HIG, Material Design)

**Apple HIG — Search fields** (`developer.apple.com/design/human-interface-guidelines/search-fields`, content verified via search-engine snippet of the live page; direct WebFetch of this URL returned only the page title because the HIG site is a client-rendered SPA that doesn't serve body content to the fetch tool):
- A search field itself is just search icon + input + clear button + placeholder text.
- For combining search with filtering, HIG sanctions two specific controls layered onto/near the search field: a **scope control** ("acts like a segmented control for choosing a category... helps someone move from a broader scope to a narrower one") and **tokens** ("a visual representation of a search term that acts as a filter").
- Explicit restraint guidance: *"To avoid overwhelming people, consider only showing filters that are relevant and contextual to what someone is looking for."*
- Also: *"consider letting people filter search results by including a scope bar in the search results content area."*

**Apple HIG — Lists and tables** (`developer.apple.com/design/human-interface-guidelines/lists-and-tables`, same SPA caveat — verified via search-engine snippet):
- Grouped list style ("headers, footers, and additional space to separate groups of data") is the sanctioned pattern for organizing a long list without extra controls.
- The alphabet index rail is the sanctioned pattern specifically for *very long, alphabetically-browsable* lists — directly applicable at 300 items if alphabetical is a plausible secondary navigation axis alongside category grouping.

**Material Design 3 — Search** (`m3.material.io/components/search/overview` and `/specs`, verified via search-engine snippet; direct fetch returned only the title):
- Two layout variants: full-screen search view (compact/phone windows) and docked search bar (medium/large windows). For a phone-only PWA, the **full-screen search view is the relevant variant** — MD3's own guidance is that the docked variant exists specifically for tablet/desktop-sized windows, which this project explicitly does not target.
- Search supports showing "suggested keywords or phrases as the user types" — i.e. autosuggest, not just substring filter.

**Material Design 3 — Chips** (`m3.material.io/components/chips`, verified via search-engine snippet):
- Filter chips are pitched as "a good alternative to toggle buttons or checkboxes" for narrowing a list — i.e. MD3 treats filter-chip rows and toggle-button groups as roughly interchangeable, which is useful validation that shadcn's `ToggleGroup` (a toggle-button abstraction) is a legitimate implementation vehicle for a chip-style filter row, not just a visual mismatch.
- Explicit wrap/scroll guidance already quoted in §1: wrap to a second row, then go horizontal-scroll beyond that.

**Material Design 3 — Lists** (`m3.material.io/components/lists`, verified via search-engine snippet):
- Lists are described as "continuous, vertical indexes of text and images used to help users find a specific item and act on it," with an optional grouping wrapper adding a heading above each sub-list — directly supports a sectioned/grouped list as a first-class, low-chrome MD3 pattern, not a workaround.

Net platform read: both Apple and Google's own design systems treat "plain list, optionally grouped/sectioned" as the default, unadorned pattern for long lists, and treat search-with-scoping and filter-chip rows as *additive* mechanisms layered on top only when the list can't be browsed structurally — not as a mandatory pairing. Both platforms explicitly warn against over-showing filters ("only show filters that are relevant and contextual").

## Per-app findings

- **Hevy** — Confirmed via official sources: exercise library combines a search bar with **filter chips for equipment and muscle target** (`hevyapp.com/features/exercise-library/`, fetched directly: "The built-in filters for equipment and muscle targets and the search bar help you find the most relevant ones"), and the Help Centre article title itself advertises "400+ Exercises and Custom Exercises" (`help.hevyapp.com/hc/en-us/articles/35688251991575-...`, title/URL confirmed via search though the article body itself 403'd on direct fetch). Custom exercises use a **single primary muscle + multi-select secondary muscles** model (`hevyapp.com/features/custom-exercises/`, fetched directly). Overall: **search + multi-dimension filter chips, with a primary/secondary tag split.**

- **Jefit** — Confirmed via official source (`jefit.com/exercises/bodypart.php`, fetched directly): exercise database is organized primarily by **body part/muscle** (Abs, Back, Biceps, Chest, etc., plus "All"), with secondary dropdown filters for **equipment, type (strength/stretching/powerlifting/olympic), and difficulty**, combinable simultaneously; results paginate as a grid. Overall: **categorized-by-body-part with additional multi-dimension filters**, no single forced primary/secondary tag split like Hevy — more like Jefit's own faceted-filter model than a tag hierarchy.

- **Strong app** — **Could not find solid primary-source evidence for the exercise-picker's internal UI structure.** Strong's own Help Center (`help.strongapp.io/article/229-my-first-workout`, fetched directly) only says exercises are chosen "from Strong's built in Exercise Library or Create your Own" — it does not document search, tabs, or filter mechanics. A secondary, unverified-against-primary source (a third-party app review found via search, not fetched/confirmed as authoritative) claims Strong's exercise section is "just a list of exercises in alphabetical order" with no body-part division — I am flagging this explicitly as secondary/unverified, not fact. Strong does have a "Muscle Heat Map" feature, but that appears to be a *training-history visualization*, not evidence about the exercise-picker UI itself. **Net: genuine evidence gap for Strong's picker UI; do not treat the alphabetical-list claim as confirmed.**

- **StrongLifts 5x5** — This app is built around a fixed 5-exercise program (squat, bench, deadlift, row, overhead press), confirmed via `stronglifts.com/stronglifts-5x5/workout-program/` (found via search, content not independently fetched body-for-body but consistent across multiple stronglifts.com pages returned by search). Because the exercise set is fixed and tiny by design, **there is no general-purpose exercise-picker/library UI to evaluate here** — the program's simplicity is the point, so this app isn't a useful comparator for a growing 50-300-item library. Noting this explicitly rather than forcing a comparison.

- **Apple Fitness+** — This is a workout-class library, not an exercise-picker, but it's a relevant same-company data point for how Apple itself designs browse/filter at scale on a phone. Confirmed via official Apple Support documentation (`support.apple.com/guide/fitness-plus/find-workouts-and-meditations-apdcd80997be/ios`, fetched directly): browsing happens via an **Activity Types row** (category-like) plus a separate **modal Filter** action (tap Filter, then select from trainer/duration/music genre/activity type), rather than permanently-visible filter chips. This matches the HIG "only show filters that are relevant and contextual" and "bottom-sheet/modal" pattern rather than the always-visible-chip-row pattern.

## Recommendation

Given the concrete facts gathered:

1. **Do not adopt filter chips or category tabs as the primary/only mechanism yet.** At 50-300 items, single-user, both Apple's and Google's own list guidance treat a **grouped/sectioned list** as the default unadorned answer to "long list," with search and filter chrome as strictly additive. Building a persistent filter-chip row now is more chrome than the evidence supports for a single-user app where the same person defined the taxonomy.

2. **Concretely: replace the flat `<ul>` + `filterExercisesByName` in `ExercisesPage.tsx` / `WorkoutForm.tsx` / `exerciseLookup.ts` with shadcn's `Command` component** (`CommandInput` + `CommandList` + `CommandGroup` per category + `CommandEmpty`). This single component gives you, in one primitive already available in this stack: incremental search-as-you-type filtering *and* grouped/sectioned display (group by a category field, e.g. "Push / Pull / Legs / Mobility / Stretch") without adding a second UI surface. This directly matches the MD3 "Lists" grouping-wrapper pattern and the HIG grouped-list-style pattern, using a component you already have.

3. **Model categorization on Hevy's primary/secondary split, not Jefit's full facet model.** Add one required, single-select `category` field per exercise (drives the `CommandGroup` sections — e.g. Push/Pull/Legs/Core/Mobility/Stretch) and, only if it turns out to matter in practice (e.g. you actually want to find "everything lower-body regardless of type"), add an optional multi-select `tags` field later. Don't build the tags field speculatively — Hevy's own docs show the primary category alone is enough to drive browsing, and secondary tags exist there purely for a filter you haven't asked for yet.

4. **If/when a genuine cross-cutting filter need shows up** (e.g. "show me all mobility exercises regardless of body part" as a real recurring workflow, not just a hypothetical), add it as a **shadcn `ToggleGroup` with `multiple`** styled as a horizontally-scrolling chip row above the `Command` list — this is literally the shadcn primitive MD3's own chip docs validate as a toggle-button-group equivalent, and it can be added later without restructuring the underlying data model (the `tags` field from step 3 already supports it).

5. **Skip Tabs and Accordion for this use case.** Tabs (single active category, no multi-membership) fight the "mobility + lower body" cross-cutting problem described in the prompt; `Command`'s `CommandGroup` sections give you the same visual grouping without forcing a single active tab. Accordion only pays for itself if category sections need to default to collapsed to control scroll length — worth reconsidering only if 300 items inside a `Command` list feels too long even with sticky group headers, but not needed at the outset.

6. **Skip Drawer/Sheet bottom-sheet filter panels for now.** They're the right vehicle *if* you later add enough filter dimensions that they can't live inline (Apple Fitness+'s own modal Filter panel is the model to follow at that point) — but for a single required category field, an inline `ToggleGroup` row or `CommandGroup` sectioning is simpler and matches the "don't overwhelm with filters" HIG guidance better than a modal for something this small.
